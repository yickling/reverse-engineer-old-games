# Startup and the outer loop

Part of the [FDPS notes](README.md). Decompiled functions are Ghidra output, not original source. Nothing here was checked by running the game.

Disassembly of `0x291f0` (frame `0x3c`), not a decompile. The functions it calls were decompiled. The outer loop is the session, not the battle. `FUN_0002b870` keeps the map until the outcome dword is nonzero or the system menu returns nonzero, and only then does `0x291f0` look at that outcome. What each key does inside that visit is in [Turns](turns.md).

1. `0x421a8` opens `DISK.NO`. Failure prints `Can't found file 'Disk.No'` and `Please use install function.`, then `exit(1)`.
2. Opens `Disk.no` in `"rt"` and scans `%s` three times. The first two scans share one stack buffer. The third is stored at `0x643e8` and later used as a directory prefix.
3. Calls `0x3c3a6`. The following compare against 1 falls into an unconditional jump that skips the CD-ROM failure strings at `0x61c3c` and `0x61c64`. This copy never reaches those messages.
4. `FUN_00030270(0x19)` starts the two sound devices (eight channels on the second) and passes `0x19` on to `FUN_00030540`. What `0x19` counts was not read. `FUN_00029630` then loads the shared interface from `MISC.VFS` and `FIELD.VFS`: both palettes, the cursor, command window, shadow, status, message box, digits, selection bar, level-up picture, window, bars, `FDETXT.FON`, and `FDETXT00.TXT`. The font metrics, and `FDETXT00.TXT` kept at `DAT_000643d0`, are in [Text](text.md). Mode 13h follows. `0x69cf0`, `0x69cdc`, quit byte `0x643eb`, and outcome dword `0x69da0` are cleared. `0x69d54` is set to `-1` just before the dead CD check; `FUN_00030960` later stores the music track there.
5. `FUN_0002a280` is the title. It returns only after a real menu choice. Its return value is ignored. The choice's writes are what matter.
6. While quit byte `0x643eb` is 0: call `FUN_0002b870`, then switch on outcome `0x69da0`.
   - 0: nothing.
   - 1: `FUN_0002a920` plays `GameOver.saf` over a copy of the screen and fades for `0x10` steps, then the title runs again.
   - 2: `call dword [0x60304 + scenario*4]`, then `FUN_00030f80`.
   - Outcome is then cleared, so a value written by the ending does not fire again on the next pass.
7. On quit: `FUN_00029410` frees the interface, font, text, icon cache, unit array, and one triple of buffers per loaded section. `FUN_00030330` is only `FUN_0003d622`, the sound shutdown. `FUN_0003c217` exchanges a 13-byte device block; the same function runs when music is stopped and at the start of each title cycle, so it is not exit-only. Mode 03h, then the string at `0x61c80` (`Thank you for playing Flame Dragon Plus!!`).

`FUN_0002a280`, the title, decompiled:

- If `FDE.SAV` exists, its checksum matches, and the scenario byte at file `0x30c5` is not `0xff`, the first three menu-enable bytes are cleared. Otherwise they stay the dword at `0x291e0`, which is `00 02 02 00`. A row accepts Enter or Space only when its byte is 0, so a missing or empty save leaves the first and last rows choosable and the middle two refused.
- `Logo.saf` plays under `Dynasty.pal` until a key below `0x80` or the clip ends, between vertical-retrace waits.
- `FD%d` is filled with 1 or 2. `FUN_00030cb0` shuts sound down, blanks the palette, and passes `{prefix}\fd.exe`, `{prefix}\FD1.Vid`, and `{prefix}\FD1.Aud` to CRT `0x4df59`. Inferred: that is an external intro, because the three paths are an executable plus a video and an audio file and the screen is cleared around the call. It was not confirmed by running it. Sound is then started again with `0x19`, and `FUN_00030960(1)` requests track 1.
- The menu is `StBoard.cel` plus four rows of `StSel.cel`. Up and down move the row. A countdown of `0x5dc` ticks leaves the menu without taking a row; the logo then runs again and the intro number flips between 1 and 2.
- Row 0: scenario index 0, roster threshold 0, call the scenario opener, set `0x60158` to 1.
- Row 1: `FUN_00024460` draws `Load.cel` and, on confirm, copies one save slot (`0x312b + slot * 0xa28`, the same stride as the four `0xff` markers). Return `-1` stays on the menu. Any other return sets `0x60131`, and return `1` calls the between-battle function below. The slot layout is in [Save](save.md).
- Row 2: `FUN_00023df0` restores the battle at the front of `FDE.SAV` (map block, roster, unit array, camera and cursor already multiplied back by 24, scenario index) and plays `PlyPhase.saf`. The map loop then runs directly.
- Row 3: sets the quit byte.

`FUN_0002b870` reads the key once per pass. A new key is handled immediately. The same key is ignored for movement on repeats 1 through 5, then repeats. Arrows move the cursor and play `Beep.wav`. Confirm either moves the unit, opens the command on an ineligible unit, or, with nobody under the cursor, calls the system menu. That menu's return value is the loop's leave flag, and its quit path returns 1 after setting the quit byte. `FUN_000309c0` on each new tick counts to `0x4b` and, when the track is set and a status call is nonzero, starts that track again. The pass redraws through `FUN_0002bc40`. The loop returns when the outcome dword is nonzero, or when the system menu returned nonzero.

`FUN_00030960(n)` stores `n` as the track. A cleared sound byte forces `-1`. `-1` calls `FUN_0003c217`. Any other value calls `FUN_0003c5cb(n + 1)` when sound is enabled. Inferred: `n` is the music track. The map's restart of the same value is why.

Outcome 2 is not the opener. `0x60304` is the per-scenario ending, 30 pointers, from `0x3a180` for index 0 through `0x3b7f0` for index 29. Disassembly of those thirty bodies, not a decompile. Indexes 0 through 25, 27, and 28 each store their own index plus one into `DAT_00069cf4` and return. Every path in those bodies stores that same next index. Index 26, at `0x3b660`, stores 27 only when `FUN_00034290(0, 0xb3)` and `FUN_00034290(3, 0xdc)` both return a pair index. It then removes those pairs with `FUN_00025c90`, plays `WinGA26.dat`, calls `FUN_00039be0`, and stores 27. If either search returns −1, it plays `Win26.dat`, calls `FUN_0001ba10`, sets quit byte `0x643eb`, and leaves the index at 26. Index 29 plays `Win29.dat`, stores 1 into `DAT_00060158` and `DAT_00060159`, calls `FUN_0001ba10`, calls `0x3d0e0(0x7530)`, plays `GoodEnd.dat`, sets the quit byte, and stores no next index. `0x3d0e0` jumps to `0x43a20`, which waits on DOS time function `0x2c`. The count is the argument times the dword at `0x69ea8`, plus `0x1f4`, divided by `0x3e8`. `FUN_00034290(slot, id)` returns the pair index of that id on that roster slot, or −1. `FUN_0001ba10` was not read. It opens `FMer1.tmp` and `FMer2.tmp`, and when the index is `0x1d` it uses `0x20` where the other path uses `0x19`.

Before the store, the ending plays one icon script through `FUN_00021620`. Indexes 0 through 16, 18 through 25, 27, and 28 play `Win%02d.dat`. Index 17 plays `Win17-1.dat` when the check below passes, and `Win17.dat` otherwise. `FUN_00039be0`, which opens `Relive.cel`, runs after the script and before the store. Index 26's quit path and index 29 do not call it. `FUN_00023950` is called by every ending except index 26. Its body was not read. Endings other than 0, 1, 14, and 18 call `FUN_00039b80` first. That function stores 0 into `+0x40` of every unit whose side is 0, then calls `FUN_0001d690`, the death spin in [Combat](combat.md). Index 0 instead calls `FUN_00028280(0, 0)`, which sets learned-id bit 0 on slot 0.

A few endings change a unit or a script name and still store the same next index. Index 14, when byte `0x640e8` is nonzero, clears `+5` on slots 0 through 8 and stores 0 into `+0x34` of slot `0x34`. Index 17 searches slot 0 for item `0xa9`. When that pair exists and units 0 through 8 each have byte `+7` equal to byte `+8`, it removes the pair and gives id `0xdb` to slot 0, then plays `Win17-1.dat`. Otherwise it plays `Win17.dat`. Either way the next index is 18. Indexes 18 and 23, when byte `0x640e9` is nonzero, clear `+5` and copy both maximum pools into the current pools for every unit whose character id is at most `0xb`. Index 22 sets `+5` on each side-1 unit from slot `0xb` up to the slot count. Index 25, when slot 0 has no item `0xa2` and `FUN_00025210(0)` is not 8, shows scenario string `0x18` and gives id `0x62` to slot 0. The stores of 1 into `0x640e8` and `0x640e9` sit in the after-action region and were not tied to a scenario.

`FUN_00030f80` then runs the between-battle step, and it reads the index the ending just stored. If the quit byte is already set it returns at once, without the village and without the opener. The session then clears the outcome and the loop leaves. For scenario indexes other than `0x10`, `0x11`, `0x15`, `0x16`, and anything at or above `0x1a`, it draws `Village.cel` with `ShopWin.Cel` and stays in a menu until the selection returns to 0 or quit is set. Arrival at 16, 17, 21, 22, or 26 through 29 is the skipped set. The five nonzero selections call `FUN_00035a30`, `FUN_00035810`, `FUN_000355d0`, `FUN_00035d40`, and `FUN_00035f80`; those five were not read. Indexes in the skipped set call `FUN_00030960(-1)` and, unless `0x60131` is set by the load row, `FUN_000241b0` on a blank screen. Either way it saves `DAT_00060158`, stores 0, calls `(&PTR_FUN_00060074)[scenario]`, and writes the saved byte back. That table is the opener, also 30 pointers, beginning `0x20e60`, `0x20ec0`, `0x20f00`. Each one calls `FUN_00022720` (the map load: outcome cleared, camera and cursor zeroed, turn counter set to 1), then `FUN_00021620` on that scenario's icon script, then `FUN_00020c30`, then `FUN_0002d7e0`. `FUN_00020c30` draws `Chapter.saf` under `Chapter.pal` and fades the palette sixteen steps down and back up. The icon script is in [Scenario files](scenario.md).

`FUN_00023b90` is the only function that appends a roster character. The call sites, and no other function, pass these ids: scenario 0 passes 0, 1 passes 6, 2 passes 4, 3 passes 1, 6 passes 3, 7 passes 2, 8 passes 8 and then 9, 10 passes 7, 14 passes 5, 18 passes 11, and 23 passes 10. The other indexes in 0 through 29 do not call it. What the append writes is in [Units](units.md). The battle copies that roster from the front, stopping at byte 1 of the map, so an id appended when the count already equals that byte is not placed. There is no screen in the functions read here that removes a roster record or refuses to drop one. `FUN_00031930`, called from this village step, cycles which roster record is shown and leaves on confirm. It does not change the count.

The first opener also forces unit 2's `+0x25` to `0xb` and its `+0x40` to 100, and centers on unit 0. The second centers on unit 0 without that unit-2 write. The other 28 opener bodies were not decompiled past the calls above. How a scenario's files are read is in [Scenario files](scenario.md).
